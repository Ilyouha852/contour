## 1. Что на самом деле нужно заказчику

Из презентации и транскрипта (распознавание шумное, поэтому часть смыслов я восстановил по контексту) следует:

- **Постановка:** на входе одна закупка, на выходе ранжированный список, кого на неё позвать. Это условное ранжирование `score(поставщик | закупка)`, а не статичный рейтинг контрагента.
- **Работоспособность (30 баллов)** названа отсекающей. Спикер прямо предупреждает о «франкенштейновых» системах из красивых модулей, которые не собраны вместе.
- **Объяснимость** нужна дважды: почему рекомендован поставщик и почему у него такой статус или роль. Её просит бизнес.
- **Роли:** производитель, дистрибьютор, поставщик. Приветствуется своя четвёртая или пятая роль.
- **Обогащение** допускается офлайн. Можно заранее найти слабые категории и пополнить пул из открытых источников (СПб и Ленобласть). В реальном времени показывать не нужно.
- **Ограничение:** без внешних API нейросетей в рабочей логике. Поисковые API разрешены, локальные модели, по-видимому, тоже.
- **Демо:** 5 минут и 3–5 кейсов. Расчёт за 5–10 секунд нормален, минута уже проблема. Тестовые закупки придут в том же формате CSV.
- **Методология:** «не заигрывайтесь». Нужны ОКПД2 плюс веса ключевых слов из названия закупки (спикер отдельно упомянул теги).

## 3. Оценка отчёта по трём пунктам

### 3.1 Сущности: нужна переделка

Что не так:
- **Выдуманные сущности.** «Отрасль», «финпоказатели» и «сумма сделки» отсутствуют в данных.
- **Рейтинг как атрибут контрагента.** Это главная концептуальная ошибка: рейтинг зависит от закупки.
- **Нет ключевых сущностей домена:** закупки, заказчика, ОКПД2, участия.
- **Нет ролей, источников обогащения и объяснений.**
- **«ИНН уникален»** неверно без учёта КПП.

Предлагаемая модель:

| Сущность | Зерно / ключ | Назначение |
|---|---|---|
| Закупка (лот) | `lot_id` | Вход системы: тексты, цена, СМП, источник АИС ГЗ/ЭМ, дата |
| Заказчик | `customer_inn` | История «заказчик ↔ поставщик» |
| Позиция ТРУ | `lot_id` + позиция | Название и код ОКПД2 |
| ОКПД2 | код | Иерархия (класс → группа → подкласс), основа для сходства категорий |
| Участие | `lot_id` + `supplier_inn` | Факт участия и `is_winner`, основной сигнал |
| Поставщик | `ИНН` (+`КПП`) | Профиль: частоты по ОКПД2, география, СМП |
| Роль и обогащение | поставщик + источник | Роль, уверенность, источник, дата сбора |
| Рекомендация | закупка + поставщик + запуск | Скор, ранг, статус, разложение на факторы (объяснение) |

### 3.2 Стек: избыточен и пропускает нужное

Лишнее для хакатона и такого объёма:
- Kafka, Kubernetes, Kubeflow, Feast и Neo4j.
- ClickHouse и Snowflake.
- Elasticsearch.
- TensorFlow/PyTorch.
- A/B-тестирование: у системы нет пользователей, нужен офлайн-бэктест.

Упущено главное:
- **Русскоязычная обработка текста:** лемматизация (pymorphy3), TF-IDF/BM25 по названиям, нечёткое сопоставление (rapidfuzz), при желании локальные эмбеддинги (rubert-tiny2, multilingual-e5).
- **Иерархия ОКПД2** как источник сходства категорий.
- **Конкретные источники обогащения.** Отчёт просто говорит «внешние источники». Их нужно назвать (см. ниже).
- **Классификация ролей** и объяснимость.

Разумный стек:

| Слой | Выбор |
|---|---|
| Данные | DuckDB/Parquet или PostgreSQL (CSV грузится за минуты) |
| Расчёт | Python: pandas/polars, scikit-learn, LightGBM по желанию |
| Поиск | PostgreSQL FTS или rank_bm25, вместо Elasticsearch |
| API | FastAPI |
| UI | React, либо Streamlit для скорости |
| Развёртывание | Docker Compose |

Что в отчёте верно и стоит оставить: PostgreSQL, «начать с Docker Compose», метрики nDCG и Precision@K, базовая безопасность.

Источники обогащения для проверки (я их не верифицировал, нужно проверить условия использования и доступность): ЕГРЮЛ/ФНС (ОКВЭД, адрес, статус), реестр МСП ФНС, ГИСП Минпромторга (производители), реестры ФАС (РНП), открытые данные ЕИС, сайты компаний и каталоги/карты (поисковые API разрешены).

### 3.3 Архитектурные варианты: релевантен только монолит

Монолит, микросервисы и event-driven в отчёте отличаются лишь степенью оверинжиниринга. Микросервисы и события плохо сочетаются с критерием «собрано и работает» и ограничением в 5 минут демо. Их место в «пути масштабирования», который тоже оценивается (пункт 8 презентации).

Что предлагаю вместо них:

| | A. Модульный монолит + офлайн-предрасчёт | B. Retrieval + обучаемый реранкер | C. Граф/коллаборативный сигнал |
|---|---|---|---|
| Идея | Кандидаты по ОКПД2 и ключевым словам, скоринг по взвешенной формуле, объяснение из вкладов факторов | Те же кандидаты, затем LightGBM по признакам | Двудольный граф заказчик–поставщик–ОКПД2, поиск «похожих» |
| Почему подходит | Быстрее всего, полностью объяснимо, соответствует «не заигрывайтесь» | Лучшее качество, сильный аргумент для «качества рекомендаций» | Находит неочевидных кандидатов, помогает при слабой вариативности |
| Риски | Веса подбираются вручную | Нет разметки, нужны псевдометки (участие/победа по времени), хуже объяснимость | Холодный старт у 36% поставщиков, сложнее объяснять |
| Срок до MVP | Минимальный | Средний | Средний |
